# Hooks — implementation notes

> Agent-facing reference for [`docs/features/hooks.md`](../../features/hooks.md).

- `src/hooks.js` validates hooks, stores them app-level under the `hooks` key (`{ enabled, list }`), matches them (tool globs, tool family via `authorization.configToolName` plus `mcp`, the argument regex in a worker thread, origin) and runs commands: `spawn` with an allowlisted environment, stdin JSON, 64 KB stdout / 16 KB stderr caps, a process-group kill on timeout or abort, priority lowered with `os.setPriority`. `runHooks(event, payload, ctx)` returns `{ decision, reason, by, args?, context?, followUps[], suppress?, notes[] }`. Per event it keeps only what that event may do (`BLOCKING_EVENTS`, `CONTEXT_EVENTS`, `followUp` on `turn.end`, `suppress` on `attention`) and sends only that event's `EVENT_FIELDS`. Node scripts are written as `hook.js` in a fresh temp folder so Node detects CommonJS or ESM.
- A note for a hook that changed arguments carries `changedArgs: true` and `changes: [{ key, before?, after? }]` (top-level keys, values as text clipped to 2000 chars); rows saved before that keep a whole `before` object, which the card still shows.
- `src/ai-stream.js` `runSingleToolCall` runs `tool.before` after the forged-call and tool-surface checks and before the circuit breaker and `authorize`; `ask` sets `forcePrompt`, so session grants and Allow do not skip the card. Rewritten arguments of a parent-only orchestration tool are checked again with `validateControl`. `tool.after` runs before `tool_result` is emitted; background subagent results, which land later, run no `tool.after`.
- `src/hookTurns.js`: `fireTurnStart`, `fireTurnError`, `fireTurnEnd(t, { startTurn, isRunning })`. `runChatStream` calls them without awaiting: `turn.start` after the run marker is set, `turn.error` on each failure and Stop path, `turn.end` after the run marker is cleared on success, with `text` read from the assistant rows saved after the turn's user row (`assistantContent` only holds the last segment), tail-kept at 16 KB. A follow-up goes through `startChatTurn(body, lifecycle, sessionToken)` with `origin: { kind: 'hook', hookId, depth, run }`; depth ≥ 3 → not started (`limit`), chat running or `EALREADY_RUNNING` → dropped (`busy`). Outcomes go to the run log. `messages.normalizeOrigin` keeps the `hook` origin; it does not reset upstream context the way schedule/webhook origins do.
- `subagent.end`: `Scope.start` in `src/tools/subagent-orchestration.js` calls `meta.onEnd` through `fireEnd` (once per run, including a child finalized by the shutdown budget in `finish`). A run that is not cancelled awaits it before `row.finalized`, so `subagent_status` keeps saying `running` until the hooks answered and shutdown can still finalize the row meanwhile (re-checked after the await). `onEnd` comes from the `subagent` branch of `dispatchTool` and calls `hookTurns.fireSubagentEnd` with `nested: false`, so it fires at every depth, and with no signal when cancelled. The answer is `exec.subagentEnd { notes, context? }`. `subagentModelResult` reduces a subagent's result to `{ ok, text, error }`, so context does not ride on the result: `runSingleToolCall` merges it into the call's `hooks` for a waited-for run, the completion `tool_result` carries it for a background run, and `subagent_status` adds `hookContext`. `runHttp` treats `task` like `content`.
- `attention`: `attention-push.notifyAttention` (approval, ask_user) and `sendChatPush('completion')` in `runChatStream` run the hooks first when `hooks.hasHooks('attention')`, and send unless one returns `suppress`. With no attention hook the push stays synchronous.
- Handlers: `runHandler` dispatches `command` (`runCommand`), `http` (`runHttp`: fetch POST, `redirect: 'error'`, 64 KB reply cap, `send` filter, `toolApproval.safeValue` on sent args, HMAC header) and `module` (`runModule`: one shared `Worker` on `src/hooks-worker.js`, jobs serialized, terminated and lazily recreated on timeout; the source is `transform()`ed (`export default` → assignment, `import` refused) and run in a `vm` context with `ctx.log` / `ctx.match` only). `run.failure` carries a non-exit-code error into `parseOutput`.
- Redaction: `parseOutput` reads `redact` (max 8, patterns ≤ 500 chars); `runHooks` keeps it for `tool.after` as `outcome.redact`. `runSingleToolCall` runs `redactForModel` (worker, 1 s budget, literal replacement, text parts of an array) on `modelContentForTool(...)`; a timeout withholds the result with a notice. The row's `hooks` meta gets `redacted { by, withheld }` and `modelContent`; `messages.reconstructUpstreamHistory` replays `modelContent` for such rows.
- Failures in `runHooks`: `hookMatches` returns `UNRESOLVED` when `regexSearch` resolves `null` (did not finish), `runHandler` throwing becomes `failedRun(message)`, and so does a `failClosed` hook on `BLOCKING_EVENTS` that is past `MAX_PER_EVENT` or unresolved, all through `parseOutput`'s `failClosed` handling. Without `failClosed`, an unresolved or over-limit hook gets a note and a `hook_run` row and does not run.
- Project hooks: `src/projectHooks.js` reads `settings.getProject(dir).hooks`, hashes canonical JSON + referenced project files in full (`hookFiles` / `referencedFiles`: `candidatePaths` of a command or inline script that are files inside the project), and stores trust in `hook_trust (project_dir, key, hash, trusted_at)`. The cache key stats the hashed files plus `watch`, every candidate path whether or not it exists, so a script that appears later is noticed; past `MAX_WATCH` paths nothing is cached. `runCommand` runs `hook.scope === 'project'` hooks (project and project-extension) from `projectDir`, which is what the hash resolved against, and passes the chat's folder as `MOUAIF_WORKING_DIR`. `active()` returns hooks only when the stored hash matches. `append()` keeps trust only if the list was trusted (or empty) before. `PUT /api/settings/project` and `update_settings` refuse `hooks`.
- Per-chat hooks: `src/chatHooks.js`, table `chat_hook (project_dir, chat_id, hook_id, entry, created_by, created_at, status, position)`, max 20 per chat. `runHooks` appends `chatHooks.active(projectDir, chatId)` (marked `scope: 'chat'`) after the app list; the app master switch and `MOUAIF_NO_HOOKS` cover them. New ids avoid app hook ids. `promote` appends to the app list, then removes the chat row. The chat DELETE route calls `removeChat`.
- Model tools: `src/tools/hooks.js` (`hook_create`, `hook_list`, `hook_delete`; mouaif family). `runSingleToolCall` sets `forcePrompt` for `hook_create` and builds the card's summary with `describe(args)`. A request that fails `draft()` is answered with `EBADINPUT` before any card. The card's decision payload carries `hookScope`, and the runner takes the lower of the request and the pick; no payload = `chat`. Specs are not pushed for nested subagents, and the runner refuses them with `EPARENT_ONLY`. `hooks.HOOK_TOOLS` are skipped by tool events in `runHooks`.
- Run log: `hook_run` table in the app DB (`logRun`, `listRuns`), one row per executed hook plus one per follow-up outcome, never pruned; `listRuns` returns at most `MAX_LIST_RUNS` (200).
- `src/server-handlers-chats.js` `runChatStream` runs `prompt.submit` after the running-chat check and before the user row is saved, then checks again that no other run started. A block returns `409 { code: "EHOOK_BLOCKED", error, hook }`. MCP App messages pass `hookOrigin: 'app'` through `startChatTurn`.
- Rows keep `hooks: { notes, context? }` in the `hooks` column of `message_store` (user rows and tool result rows). `messages.withHookContext` appends `context` when history is rebuilt upstream. The stream sends `prompt_hooks { clientId, seq, hooks }` so the open page shows a prompt's context block at once.
- `hooks` is not in `CLIENT_SETTINGS_KEYS`: `update_settings` cannot write it, and `PUT /api/settings/app` refuses it. The routes below are the only way in, behind the normal session and access gates:

```
GET  /api/hooks                              -> { enabled, list, events, origins, families, shells, disabledByEnv }
GET    /api/chats/:id/hooks?projectDir=                 -> { hooks: [{ hook, createdBy, createdAt, status }], runs, max, hooksOn }
POST   /api/chats/:id/hooks { projectDir, entry }       -> { hook }   (added by the user)
PUT    /api/chats/:id/hooks/:hookId { projectDir, entry?, status? } -> { hook }
DELETE /api/chats/:id/hooks/:hookId?projectDir=         -> { ok }
POST   /api/chats/:id/hooks/:hookId/promote { projectDir, scope: "app" | "project" } -> { ok, hook }
GET    /api/hooks/project?projectDir=                -> { hooks, errors, files: [{ path, bytes, text, truncated } | { path, missing }], hash, trusted, trustedHash, changed }
POST   /api/hooks/project/trust { projectDir, hash }  -> the same (409 when the hooks changed since that hash)
DELETE /api/hooks/project/trust?projectDir=           -> the same
GET  /api/hooks/runs?projectDir=&chatId=&limit=
                                             -> { runs: [{ id, at, hook, name?, event, decision, ms?, detail?, error?, projectDir?, chatId? }] }
PUT  /api/hooks  { enabled, list }           -> the same shape, after validation (400 with the first problem)
POST /api/hooks/test { hook, payload?, projectDir? }
                                             -> { parsed, code, ms, timedOut, stdout, stderr }
```

- Frontend: `frontend/src/components/SettingsHooks.jsx` (page at `#/settings/extensions/hooks`, linked from the Hooks row of `SettingsExtensions.jsx`; `#/settings/hooks` is a legacy alias in `routes.js`; recent runs, exported `HookEditor`), `components/settings/hookText.js` (labels and summaries), `components/chat/HooksDock.jsx` (the chat's hooks bar and panel; `stream.js` fires `CHAT_HOOKS_CHANGED` from `hookEvents.js` after hook tools), the `hook_create` scope picker in `components/chat/cards.js`, `components/settings/ProjectHooksReview.jsx` (review + trust, used by Settings and `components/chat/ProjectHooksBar.jsx`), `components/chat/hookNotes.js` (tool-card line, approval card list, prompt block), the follow-up badge in `components/chat/transcript.js`.
- Tests: `node scripts/test-hooks.js` (includes a full turn against a mock provider: the follow-up chain to its cap, and `turn.error`).
- The wider design (project hooks with trust, per-chat and model-made hooks, `turn.end`, UI extensions) is in [the extensions spec](../specs/extensions.md); this is its phases 1 to 4.

## Boundaries — the tightening surface

What keeps hooks from being a full extension API, and where each limit is enforced. The user-facing summary is [What hooks cannot do](../../features/hooks.md#what-hooks-cannot-do).

- **No `allow`, ever.** `parseOutput` accepts only `continue | block | ask`; `BLOCKING_EVENTS`, `MAX_PER_EVENT` and the approval gate are untouched by hooks. A hook can never skip `authorize` or turn an `off` tool on — the gate sees the (possibly rewritten) arguments only.
- **Per-event stripping** in `runHooks`, right after `parseOutput`: `ask` and `updatedArgs` survive only on `tool.before` (line ~798), `context` only on `CONTEXT_EVENTS`, `followUp` only on `turn.end`, `suppress` only on `attention`, `redact` only on `tool.after`. Adding a new decision means adding it to the event list here, to `EVENT_FIELDS` and to the parser, or it is silently dropped.
- **No request transform.** `turn.start` is fire-and-forget (`hookTurns.fireTurnStart`); nothing calls the model's request builder through a hook, so the system prompt, model choice, message list and provider payload are unreachable. `prompt.submit` sees the prompt text only (no images, no model) and can only block or add context. `tool.after` can `redact` the result toward the model (`redactForModel`) but cannot substitute it, and a background subagent's result never runs `tool.after`.
- **No lifecycle events.** `EVENTS` is the whole list. There is no chat create/fork/delete, settings, provider/model, MCP server lifecycle or file/shell event, and no hook on the outgoing request. A feature that needs one is a core change, not a hook.
- **Reach of each handler.** `module` runs in `src/hooks-worker.js`: one shared worker, vm context with `codeGeneration: { strings: false, wasm: false }`, `import`/`import()` refused by `transform`, so no `require`, `process`, `fetch`, `fs` or timers — `ctx.log` and `ctx.match` only. `command`/`script` spawn with an allowlisted env, stdin JSON, a process-group kill on timeout/abort and lowered priority. `http` POSTs with `redirect: 'error'`, an HMAC header and the `send` filter. `mcp` calls one tool on the extension's own server.
- **Calls that fire no hooks.** Composer-initiated calls (`/shell`, `@action`, direct MCP), cardless tools, subagent tool calls without `subagents: true`, and `HOOK_TOOLS`. `attention` fires only for approval, `ask_user` and completion pushes.
- **Budgets:** `MAX_HOOKS = 50` per list (app, project, chat and extension each), `MAX_PER_EVENT = 4` executed per event per call (a skipped `failClosed` hook blocks), `MAX_CONCURRENT = 8` processes, `MAX_CONTEXT = 8 KB` per event, follow-up depth 3, `DEFAULT_TIMEOUT_MS = 5000` within `MIN_TIMEOUT_MS`/`MAX_TIMEOUT_MS`, `MAX_MODULE = 64 KB`, `MAX_SCRIPT = 64 KB`, 64 KB stdout / 16 KB stderr, `MAX_REDACT = 8`, run listing capped at `MAX_LIST_RUNS`.
- **Non-hook capability** lives elsewhere: extension `ui` slots and host tools (`src/extension-host-tools.js`: `mouaif/chat.badge`, `composer.insert`, `settings.get/set`, `chat.recent`, `chat.open_sheet`), `model.context` app context (`src/app-context.js`) and host events. Prompt/request transformation and app lifecycle events stay core-only.
