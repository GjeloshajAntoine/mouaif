# Native file tools — implementation notes

> Agent-facing reference for [`docs/features/file-tools.md`](../../features/file-tools.md). The human-facing surface lives in that file; the implementation details, wire shapes, and source paths live here.

## HTTP surface

| Method | Path | Purpose |
|---|---|---|
| `PUT` | `/api/settings/project` | Toggle `tools.file.enabled` (same payload as `tools.shell.enabled`) |
| `GET` | `/api/tools/authorization?projectDir=…` | Read the resolved `tools.file` config |
| `PUT` | `/api/tools/authorization` | Set `tools.file.mode` / `allowlist` (same shape as `tools.shell`) |
| `GET` | `/api/chats/:id/tool-preview?projectDir=…` | Returns the file-tool specs the model would see, with `fileToolsEnabled: true/false` and the five entries listed in `tools` |

The file tools are dispatched by the same `tool_call` flow as the shell tool inside the AI client. There is no separate `/api/tools/file/*` HTTP endpoint — the model-facing tools all run in-process through the same dispatcher.

## Implementation notes

- New module: [src/tools/files.js](../../../src/tools/files.js). Public surface: `SPECS` (five OpenAI-compatible function specs), `FILE_TOOL_NAMES` (frozen array of the five), `isFileToolName(name)`, `runFileTool(name, opts)`, `resolveSandbox(projectDir)` (re-export of the shell tool's helper for parity).
- `search_files` is a thin adapter: `runSearchFiles()` delegates to [src/tools/searchEngine.js](../../../src/tools/searchEngine.js), which owns both backends (ripgrep via `--json` NDJSON over a spawn, and a 16-way-concurrent JS walk), binary discovery (`MOUAIF_RG_PATH`, `PATH`, then the VS Code / codex bundled copies), pattern normalization (`(?i)` peeled into `--ignore-case`; `(?s)` and the other unsupported constructs are refused with `EBADINPUT` so a search can never return a row it cannot redact), path scoping, and the `include` glob (brace alternation and character classes, implemented identically on both backends). Both backends return `{ query, matches, filesScanned, truncated, engine, capMatches?, capBytes?, filesSkipped? }`, where `filesScanned` is the number of files with at least one match. See [docs/features/search-engine.md](../../features/search-engine.md) and [docs/agent/features/search-engine.md](search-engine.md).
- The AI client collects file-tool specs alongside shell and MCP specs in [src/ai.js](../../../src/ai.js) `streamChat` and reduces them through `promptProfiles.reduceToolSpecs` like every other advertised tool, so the per-profile tool budget is uniform across shell, file, and MCP.
- The dispatcher in `streamChat` (`dispatchTool` in [src/ai.js](../../../src/ai.js)) routes all five names to `runFileTool`. `write_file` intentionally writes the complete supplied body. `edit_file` is a distinct, non-destructive replacement operation: it accepts `path` or `file`, requires `oldText` and `newText`, and returns `ENO_MATCH` or `EMULTI_MATCH` without changing the file when the target is stale or ambiguous. Matching treats `LF`, `CRLF`, and legacy `CR` as equivalent. It first collapses horizontal whitespace, then safely retries with formatter layout ignored: line wraps, blank lines, indentation, and whitespace around punctuation may differ, but separators between word characters, quoted-string content, and punctuation itself must still match. The unique match position is mapped back to the original source byte offsets, and replacement lines use the target file's dominant line ending, so an LF payload can safely edit a CRLF checkout without producing mixed endings. It writes through a temporary sibling and rename so interruption cannot leave a partial file.
- Matching is relaxed where it was needlessly strict, without weakening the path-safety contract: `list_files` treats a bare directory pattern (`src`) as `src/**` and matches globs case-insensitively, so "list src" and `README*` return results instead of an empty list; `search_files` treats a misspelled or not-yet-created `path` as a subtree search under its nearest existing ancestor instead of silently returning zero matches; and `parseReferences` in [src/tags.js](../../../src/tags.js) resolves bare `@basename` mentions against the tagged map (then the on-disk scan) when the exact path is unknown.
- The authorization module ([src/tools/authorization.js](../../../src/tools/authorization.js)) now treats `file` as a native tool alongside `shell`. The `NATIVE_TOOLS = new Set(['shell', 'file'])` set is the single source of truth; adding a future native tool is a one-line addition. The per-tool summary on the "Authorization required" card is `args.path` for file tools (so the allowlist regex can match the path), `args.cmd` for `shell`, and the first string argument for MCP tools.
- The path-safety contract is the same as [src/tags.js](../../../src/tags.js): every model-supplied path is normalized to POSIX-relative, then resolved back through `realpath` (walking up to the first existing ancestor for `write_file`-style paths that don't exist yet), with the same `EOUTSIDE_PROJECT` error shape. Symlinks that point outside the project root are rejected.
- Mobile UI ([frontend/src/components/SettingsProject.jsx](../../../frontend/src/components/SettingsProject.jsx)): the **File tools** row in the project Tools tree, with the same Off / Ask / Allow segment and Off ↔ Ask checkbox shortcut as every other tool row. The allowlist `<textarea>` was removed from Settings → Project; `tools.file.allowlist` patterns in `.mouaif.json` are still honored but are edited from the raw JSON (Technical details).
- Tests: [scripts/test-file-tools.js](../../../scripts/test-file-tools.js). Coverage includes glob compilation, OpenAI spec shape, `resolveSandbox`, every tool's happy path and error paths (`EOUTSIDE_PROJECT`, `EBADINPUT`, `ETOOL_CAP`, `EUNKNOWN_TOOL`, `ENOENT`), line-ending-tolerant `edit_file` matching in both directions, mixed-ending ambiguity detection, the `list_files` skip-dir behavior, the `search_files` path-filter and bad-regex paths, the `write_file` overwrite + nested-directory creation, and the `fileReadMaxBytes` cap override.

## Images (`read_file`)

Human-facing page: [docs/features/read-file-images.md](../../features/read-file-images.md).

- `runReadFile` in [src/tools/files.js](../../../src/tools/files.js) branches before the text read: `isImageExt(ext) && !TEXT_EXTS.has(ext)` routes to `readImageFile`, so `.svg` (on the text allowlist) keeps returning markup while `.png` / `.jpg` / `.jpeg` / `.gif` / `.webp` / `.bmp` / `.ico` return pixels. The extension list and the ext → MIME map come from `src/files.js` (`isImageExt`, `mimeForExt`) — the file editor's table, so the editor and the tool cannot drift.
- The result object is `{ relPath, kind: 'image', mimeType, bytes, note, content: [{ type: 'image', data, mimeType }] }`. The `content` block is deliberately the MCP image shape, so `toolResultImageParts` in [src/ai-stream.js](../../../src/ai-stream.js) forwards it as a native vision part (`{ type: 'image_url', image_url: { url: 'data:…' } }`) with no provider-specific code, and `openAIContentToAnthropic` / `openAIContentToGeminiParts` in `src/ai-endpoints.js` convert it for Anthropic and Gemini. `webpreview` is the only native tool that opts out of that path.
- The model-facing string is a three-line header (`# File:` / `# Kind: image (<mime>, <bytes> bytes)` / `# <note>`) and never contains base64. On the live path `compactToolFeedback` then rewrites the tool message to the sanitized JSON of the result — `omitImagePayloads` replaces the `data` field with `[image payload omitted; attached separately]`, so the payload is transmitted exactly once, as the vision part.
- Cap: `fileReadMaxImageBytes` (default `DEFAULT_READ_MAX_IMAGE_BYTES` = 4 MiB, exported for tests) read from the app-level settings blob the dispatcher passes as `settings` (same plumbing as `fileReadMaxLines`). Over-cap reads throw `ETOOL_CAP` carrying `{ size, cap }`.
- `runListFiles` now accepts image extensions alongside `TEXT_EXTS` and returns `{ path, image: true }` for them; the text form appends ` (image)` to those rows. `search_files` still walks text extensions only.
- Frontend: `renderReadFileToolResult` in [frontend/src/components/chat/toolRender.js](../../../frontend/src/components/chat/toolRender.js) branches on `kind === 'image'` to `renderReadFileImage` (thumbnail from the data URL inside a `.tool-card__image-button`, plus `Sent to the model as an image.`), and `openImageLightbox` appends a fixed full-screen overlay to `document.body` that closes on the button, on Escape, and on a backdrop tap. `parsePlainFileToolResult` + `formatResultSummary` in `frontend/src/components/chat/tools.js` re-read the text header so a replayed or nested result still reports `kind`, MIME type, size and the `PNG · 70 B` summary; `parseListEntriesBody` strips the ` (image)` suffix back into `{ image: true }`.
- Styles: [frontend/src/tool-cards.css](../../../frontend/src/tool-cards.css) (`.tool-card__image-button`, `.tool-preview__image-note`, `.image-lightbox*`), mobile-first — `position: fixed; inset: 0`, `object-fit: contain`, `--tap` sized close button inside `--safe-top`.
- Tests: [scripts/test-file-tools.js](../../../scripts/test-file-tools.js) (block shape, byte fidelity, cap, `.svg` staying text, `list_files` flag, path safety) and [scripts/test-read-image-preview.js](../../../scripts/test-read-image-preview.js) (data URL, alt text, no base64 in text nodes, lightbox open/close paths, text-only fallback, list row marker).
