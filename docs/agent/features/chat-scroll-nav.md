# Chat scroll navigation — implementation notes

> Agent-facing reference for [`docs/features/chat-scroll-nav.md`](../../features/chat-scroll-nav.md). The human-facing surface lives in that file; the implementation details and source paths live here.

## Implementation

- Markup lives in `frontend/src/components/chat/Chat.jsx` (`nav.chat-view__scroll-nav`). The Bottom arrow is the old jump-to-bottom button (`refs.jumpBtn`, `.chat-view__jump`), so its counter logic is the same.
- **The rail is an overlay, not a bar.** `.chat-view__scroll-nav` is `position: absolute` in `.chat-view__transcript-box`, with `bottom: calc(24px + var(--nav-col) + var(--nav-gap))` — 54 px, one full grid level above its 24 px resting clearance. It is out of flow, so the transcript keeps the full height between the chat head and the composer. An intermediate revision made it a `flex: 0 0 auto` row inside the box: that reserved ~24 px of reading height on every phone and read as a second toolbar wedged between the messages and the composer. `scripts/test-responsive-layout.mjs` pins the current shape — it asserts `getComputedStyle(nav).position === 'absolute'`, that the transcript's bottom reaches the preview dock's (or composer row's) top minus that surface's own margin, and that Prev / Next keep identical coordinates once Latest and its badge appear.
- **The rail eyes no longer swallow <kbd>Space</kbd>.** The buttons are in the tab order and the transcript itself is focusable (`tabIndex: 0`, `aria-label="Chat transcript"`), so <kbd>Space</kbd> scrolls the focused transcript and activates a focused navigation button. The earlier revision kept the rail at `tabIndex: -1` because a focusable button swallowed Space; that is solved by focus, not by hiding the buttons from the keyboard. `test-responsive-layout.mjs` Tab-walks to `--prev`, presses Space on the transcript and asserts it scrolls, then focuses Latest, presses Space and asserts `data-mode` returns to `pinned` with focus back on the transcript.
- **Hiding focused Latest must not drop focus on `body`.** `updateJumpButton()` returns focus to the transcript with `{ preventScroll: true }` before hiding the button (covered by `scripts/test-chat-scroll-nav.mjs`).
- **Next stays rendered but disabled while pinned**, instead of being display-hidden: the two message targets must not swap places. `updateJumpButton()` sets `nav.querySelector('.chat-view__nav-btn--next').disabled = pinned`.
- The painted control is 20 px with a transparent `::before` at `inset: -4px` filling its 28 px slot. The column used to be 44 px slots around 26 px pills; at that size it read as "way too big" and cost every row 36 px, so it was shrunk on request. Do not grow it back. Both `width`/`height` on the button are required, not just `min-*`: a flex item ignores a bare min-size without a definite size.
- **The rail never covers the transcript's scrollbar.** `.chat-view__transcript-box` also declares `--nav-scrollbar: 0px`, which `syncNavScrollbarLane(refs)` in `frontend/src/components/chat/scroll.js` overwrites with the lane the bar actually takes: `offsetWidth - clientWidth - clientLeft` of the live scroller (the total inline inset minus the left one, which is the left border or the mirrored gutter, never the bar). The rail's `right` is `max(safe-area + var(--nav-scrollbar), (100% - --read-max) / 2 - var(--nav-col))`; with the rows back to their full width, the frame-edge term is what puts the rail flush against the bar's lane on every phone, so the rail's right edge is never past the lane's left edge. Before this, the rail hung off the transcript box while the bar was painted inside the scroller nested in it, so as soon as the window was narrow enough to put the rail at the frame edge — 768–900 px on a desktop, where the reserved 10 px lane starts at the transcript's right edge — a 28 px rail overlapped the bar by 2 px and swallowed its drag; `elementFromPoint` at the pill's row returned `chat-view__nav-btn--prev` where the bar should have been. Measured in JS rather than derived from the 48 rem breakpoint, because an overlay scrollbar (every phone, macOS) reserves nothing and a classic one is as wide as the platform makes it. Re-measured from the transcript's `ResizeObserver` callback (which also re-pins), so platform, width and zoom changes are all covered, and `syncNavScrollbarLane` only writes when the value actually changes. `scripts/test-chat-scroll-performance.js` unit-tests the measurement (reserved lane, overlay scrollbar, ungutter'd bar, a left inset that must not be counted, and a detached view); `scripts/test-responsive-layout.mjs` asserts, wherever the lane is wider than zero, that every pill ends at or before the lane's left edge and that `elementFromPoint` on the lane returns the scroller rather than a pill.
- **The rail reserves no strip.** The rows are back to the plain reading column (`width: 100%; max-width: --read-max; margin-inline: auto`). A `--nav-gutter` reservation used to shorten every row so the rail had a lane of its own; measured on a phone that cost each message 20 px of width (rows ended at 332 px of a 352 px column at 360 px) to protect a corner the rail only occupies at the bottom. It was removed on request: *"Remove added Space — move the buttons to allow using the scroll bar."* The rail's `right` stays `max(safe-area + --nav-scrollbar, (100% - --read-max) / 2 - --nav-col)`, so it now sits flush against the scrollbar's lane below the wide breakpoint (over the last row's corner) and just past the reading column above it. `test-responsive-layout.mjs` asserts the rows still reach the reading column at every width — the assertion that fails by 20 px if the reservation comes back. This replaced the old `padding-right` reservation on top-level `.tool-card--progress`, which protected only that one card.
- **The rail is a one-column grid of `--nav-col` slots.** `grid-template-columns: var(--nav-col); grid-template-rows: repeat(3, var(--nav-col))` with a 2 px gap: Prev (row 1), Next (row 2), Latest (row 3, kept allocated while hidden so Prev / Next never move). Latest's badge is `position: absolute` on the pill's top-right corner instead of widening the pill, so it stays inside the control's own 28 px column. Each 20 px pill is centred in its slot, so every expanded hit area stays inside its own slot and never overlaps a neighbour. The previous revision made the buttons themselves 50 px wide labelled pills (`3.5rem` columns): they covered a row of transcript text. Keep the slots equal to `--nav-col` so each hit area stays inside its own slot.
- **No visible text.** `aria-label` + `title` carry the meaning of each glyph; the only text any control renders is Latest's unread badge (`.chat-view__jump-count`). A label span moved the buttons under the user's finger and made the cluster read as a toolbar.
- `updateJumpButton(refs)` in `frontend/src/components/chat/scroll.js` changes the rail's `data-mode` (`pinned` / `free`) and its visibility directly on the DOM, so scrolling never re-renders Preact. `noteTranscriptScrollTop(refs, scrollTop)` reuses the `scrollTop` the scroll listener has already read to decide whether the transcript overflows. It adds no layout read.
- `scrollToAdjacentMessage(refs, dir)` reads row positions only when an arrow is tapped. The rail sits outside the transcript, so the user-intent tracker cannot see the tap. The function therefore unpins on its own and cancels any pending re-pin, which stops the scroll listener from pulling the view back down. Off-screen rows use `content-visibility: auto` placeholders, so the function lines the row up again for up to three frames as the real layout arrives.
- `findAdjacentMessage(tops, line, dir)` is the pure lookup, covered by `scripts/test-chat-scroll-nav.mjs` (part of `npm run test:chat-view`).
- The rail lives in `.chat-view__transcript-box`, a positioned wrapper that takes the transcript's flex slot. The rail's `bottom` is measured from the transcript itself, not a fixed offset from the bottom of the chat view.
- A single tap always moves the view by at least 48 px, which is the `isNearBottom()` pin threshold. Without that floor, "previous" at the bottom picked the row cut off a few pixels above the top edge. The tap then barely moved the view, landed back inside the pin band, and re-pinned straight away, so the arrow looked dead.
- "Next" re-pins when the next row can never reach the top, because the view is already scrolled as far as it goes. The rail then returns to its pinned state, rather than unpinning with nothing left to scroll.
- Transcript rows have `flex-shrink: 0`. The transcript is a height-bounded flex column, and an off-screen `content-visibility: auto` row has a min-content height of 0. Shrinkable rows therefore collapsed to nothing, which broke both the scrollbar and the row offsets the arrows jump to.
- `node scripts/chat-scroll-nav-fixture.mjs [port]` serves the real chat view with a long fake transcript and in-page API stubs. Open it at a phone viewport to check the arrows by hand.

### Layout constraints the rail depends on

The bottom offset, the 48 px floor and `flex-shrink: 0` are all layout contracts rather than styling choices: change any of them and an arrow either sits on the composer, reads as dead, or jumps to the wrong row. The fixture above is the way to re-check them by hand after touching the transcript's box model.
