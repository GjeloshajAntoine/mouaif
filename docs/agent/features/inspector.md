# Inspector — custom DevTools-style mobile UI — implementation notes

> Agent-facing reference for [`docs/features/inspector.md`](../../features/inspector.md). The human-facing surface lives in that file; the implementation details, wire shapes, and source paths live here.

## REST surface

| Method | Path | Body | Response |
|--------|------|------|----------|
| GET    | `/api/inspector/config` | — | `{ url, defaultUrl }` |
| PUT    | `/api/inspector/config` | `{ url }` | `{ url }` (rejected with 400 if `url` is not http(s)) |
| GET    | `/api/inspector/version` | — | Chrome `/json/version` payload |
| GET    | `/api/inspector/targets` | — | `{ targets: ChromeListItem[] }` |
| POST   | `/api/inspector/open` | `{ url }` | `{ target: ChromeListItem }` — opens the URL in a new Chrome tab and returns the fresh target. Primary path is the CDP `Target.createTarget` command over the browser-level WebSocket (from `/json/version`); falls back to the classic `PUT /json/new` for Chrome builds that still expose it (modern Chrome 137+ removed the HTTP endpoint and returns 404). If the CDP browser WS id went stale (Chrome restarted between the `/json/version` fetch and the WS open — Chrome answers "not found"), the call retries once with a freshly re-fetched id. If `/json/version` has no browser WS **and** `/json/new` 404s, a clear actionable error is returned instead of Chrome's raw "not found" |
| POST   | `/api/inspector/close` | `{ targetId }` | `{ ok: true }` — closes a tab (`Target.closeTarget` on the browser-level WebSocket) |
| POST   | `/api/inspector/reload` | `{ targetId }` | `{ ok: true }` — reloads a tab (`Page.reload` on the target's WebSocket) |
| POST   | `/api/inspector/navigate` | `{ targetId, url }` | `{ frameId, loaderId }` — navigates a tab to a new URL (`Page.navigate` on the target's WebSocket). `url` must be http(s) |
| POST   | `/api/inspector/history` | `{ targetId }` | `{ index, canGoBack, canGoForward, entries: [{ entryId, url, title }] }` — the tab's session history (`Page.getNavigationHistory`). Read-only; what the nav row's two arrows use to know whether they have anywhere to go |
| POST   | `/api/inspector/back` | `{ targetId }` | `{ ok: true, wentBack: <bool> }` — steps one entry back (`Page.getNavigationHistory` + `Page.navigateToHistoryEntry`). `wentBack: false` means there was nothing behind, which the UI shows as a no-op |
| POST   | `/api/inspector/forward` | `{ targetId }` | `{ ok: true, wentForward: <bool> }` — the same step in the other direction, for a tab the user navigated back from |

Errors from the upstream Chrome are mapped to typed status codes:

| Code | HTTP | When |
|------|------|------|
| `ECHROME_UNREACHABLE` | 502 | The configured host didn't accept the TCP connection |
| `ETARGET_NOT_FOUND`   | 404 | `targetId` was not in `/json/list` |
| `EUPSTREAM`           | 502 | Chrome returned a non-2xx from `/json/list` or `/json/version` |
| `EPARSE`              | 502 | Chrome returned 2xx with a non-JSON body or a non-array for `/json/list` |
| `EBADURL` / `EBADINPUT` | 400 | Mis-shaped input |

The WebSocket proxy returns 400 for missing `targetId` / `ws`, 404 for unknown targets, 502 for `ECHROME_UNREACHABLE`, and a 500 with a typed body for upstream open failures. On success, the response is the standard `HTTP/1.1 101 Switching Protocols` and the connection is upgraded.

## Implementation notes
### Inspector sheets are portalled to the document root
The Inspector's overlays (detail, confirm, Chrome profiles and the style editor) used to render where the panel that owns them renders. The style editor is owned by the Styles panel, so it was mounted **inside** `.inspector__styles` — a scroller (`overflow-y: auto`, `-webkit-overflow-scrolling: touch`) nested inside the page's own scroller, `.app__main`. `position: fixed` normally escapes an ancestor like that; where the scrolling ancestor becomes the overlay's containing block, it does not, and `inset: 0` then resolves against the scroller's padding box, so the overlay is the size of the scroller and its content is clipped by the scroller's overflow. Only the sheet *body* scrolls, so a sheet header pushed above the scroller's top is unreachable, and the backdrop covers only the panel body — the rest of the app still looks interactive.
- **Reproduced** in Chrome on a 393 × 852 viewport against `http://127.0.0.1:8777/` (the styles fixture), with the (then) Add-property sheet open — it was owned by the same panel — and the containing block forced the way a phone hands it to a fixed descendant of a scroller (`.inspector__styles { transform: translateZ(0) }`):
	- before — overlay `0…960` (960 px, the viewport), `offsetParent` null, sheet top `134`, head `134…197`, `elementFromPoint` at Close's centre → `btn inspector__sheet-close`;
	- after — overlay top `-725`, 497 px tall (the scroller box), sheet top `-1053`…`-228`, head `-1053…-990`, `elementFromPoint` at Close's centre → `null`.
- **Fix:** `sheetPortal(node)` in [frontend/src/components/inspector/sheetPortal.js](../../frontend/src/components/inspector/sheetPortal.js) — `createPortal(node, document.body)` with a `typeof document === 'undefined'` guard so a non-DOM render still returns a node. This is the same root mounting `DraftCraftAnnotator.jsx` uses ("Render the modal at the document root so the app dock cannot paint over it") and the same class of remedy as `ModelPickerField.jsx`'s `showModal()` top-layer sheet.
- **No CSS moved with it.** Every `.inspector__overlay` / `.inspector__sheet` rule is a plain class selector with no ancestor dependence (checked across `inspector-*.css`), so the sheets keep their 44 px targets, safe-area padding and `vh` → `dvh` ceilings at the root. Verified in the browser after the change: overlay back to `0…960`, head `134…197`, Close and the property name field both hit-test to themselves **with the containing block still forced**, Apply wrote `position: relative` (receipt `1 change · 1 added`), and the **Discard this change?** confirm sheet portals too (both of its buttons hit-test to themselves).
- **The `document.body` parent is also what makes the backdrop honest.** With the overlay at the root, a tap anywhere outside the sheet reaches the overlay and closes it; inside the panel it only covered the panel body.
- **Guarded** by `scripts/test-inspector-touch-controls.js`: for each of `ConfirmSheet.jsx`, `DetailSheet.jsx`, `InspectorProfilesSheet.jsx` and `StylesPanel.jsx`, it asserts the file imports `sheetPortal` and that the number of `class: 'inspector__overlay'` occurrences equals the number wrapped in the portal, plus that no sheet is left as a bare `return h('div', { class: 'inspector__overlay'`. Run against the pre-fix sources, those checks fail. The Add-property browser is guarded the other way round — see the next section.
### The Add-property browser is a section of the panel, not a sheet (`AddPropertyBrowser.jsx` + `inspector-touch.css`)
The property cards started life as the bottom sheet described above (`AddPropertySheet.jsx`, `.inspector__sheet--addprop`, an 86 dvh overlay with a backdrop). Two separate things were wrong with that, and only one of them was a bug.
- **It covered the question's context.** Choosing a property is a question *about the element the panel is showing*: the pinned live preview, the identity row and the controls already set are what every card is being compared against. A viewport-sized sheet with a scrim put all of it behind the question, on the one screen where the user is comparing.
- **It could be laid out against the panel's scroller** — the bug measured above (overlay 497 px instead of 960, head at `top -1053`, `elementFromPoint` at Close → `null`). Portalling to `document.body` fixes the geometry, but keeping a full-screen overlay for a choice that is *about* the panel is the wrong shape regardless.
- **The fix is structural:** the cards are now a normal block rendered by the panel between **Style controls** and **Declared styles**, directly under the **＋ Add property** button (`AddPropertyBrowser.jsx`, class `.inspector__addprop`, `id="inspector-addprop"`, `role="region"`). Nothing is `fixed`, nothing is portalled, and the only scroller is the panel's own `.inspector__styles` — so the search field, the chip row, the cards, the **Close** button and everything above them are all in one scroll. Re-measured on the repo's own server (port 18400, viewport 375 × 667, styles fixture connected, `#hero` selected): the block mounts inside `.inspector__styles` (`inOverlay: false`), the head lands just below the sticky pin (block `top 437` vs pin `bottom 431`), **Close** and the search field both hit-test to themselves, and 31 cards render for **All**.
- **The trigger is a disclosure, not an action.** `onAddProperty` toggles (`setAddOpen((open) => !open)`) and the button carries `aria-expanded` + `aria-controls="inspector-addprop"` with a title that flips between "Browse CSS properties…" and "Hide the property list". Measured: `aria-expanded` `false → true → false`, the `is-open` class applied and removed, and the block mounted/unmounted with it. With a sheet, a second tap on the trigger was hidden behind the scrim — inline, the same tap must close what it opened.
- **The browser asks the panel to bring its own head into view.** Switching group (or typing a search) replaces every card below the controls while `.inspector__styles` keeps its offset. The old sheet reset `scrollTop = 0` on its own scroller; inline there is no such scroller, so the browser calls the panel's shared `revealInPanel(node.closest('.inspector__styles'), node)` — the same helper the group chip row uses, so the sticky pin is measured and the head is never placed under it — from an effect keyed on `[group, query]`, and from the open effect (which also resets the group to `all` and the query to `''`). Measured: switching from the end of **All** (`scrollTop 4248`) to **Layout** landed at `1443`, with the head, the search field and the chip row all hit-testing to themselves.
- **No `vh`/`dvh` ceiling, and that is the point.** The block has no ceiling to get wrong — the panel clips nothing, so all 31 cards are reachable — which is why the old `.inspector__sheet--addprop` ceiling rules were deleted rather than re-styled. Verified by scrolling the panel to its end and hit-testing the last card and the closing note.
- **`.jsx` is invisible to `node -c`.** A hook used but not imported builds cleanly and then throws on the first render, taking the panel with it. `scripts/test-inspector-touch-controls.js` checks `AddPropertyBrowser.jsx`'s import list against the hooks it calls, the same check `StyleControls.jsx` and `StylesPanel.jsx` already carry.
### Styles panel: scrolling a card you just changed
Two navigations in the Styles panel (`frontend/src/components/inspector/StylesPanel.jsx`) replace content under a scroller that keeps its own offset. Both were reproduced in Chrome at 360 px against a real debug target, and both are now guarded by `scripts/test-inspector-touch-controls.js`.
- **Switching group.** The six group chips replace every card below them. `.inspector__styles` is the panel's own scroller (`overflow-y: auto`), and swapping content shorter than the current offset clamps `scrollTop` to the new maximum — measured after reading the bottom of the **Text** group and tapping **Spacing**: `scrollTop 3055`, chip row at `top -2412`, new group entirely above the viewport. The tap read as "the panel emptied".
	- The chip row's node is owned by the surface (`StyleControls.jsx`, rendered `ref: props.tabsRef`) and the scroll is owned by the panel, exposed as `props.revealRef` — a closure reassigned every render. `revealInPanel(scroller, node)` lives in `StyleControls.jsx` and is shared with the tree path.
	- **The reveal must measure the pinned chrome, not the scroller.** Two strips are `position: sticky` and opaque at the top of `.inspector__styles` — `.inspector__styles-pin` (the element identity row) and `.inspector__touch-tabs` (the group chip row, which only pins once the user has scrolled past it) — so a node aligned to `bounds.top` lands *underneath* whichever is lowest. The visible region starts at `max(bounds.top, chromeBottom)`, where `chromeBottom` is the bottom edge of each strip that is **actually pinned** (`box.height && box.top <= bounds.top + 1`), and it is measured fresh each call because the pin's height follows its content (the label wraps differently per element, and a failed tree hop adds an error line). A zero-height scroller returns early — there is nothing to bring anything into.
	- **The pin's height is published, not hard-coded.** The group chip row pins at `top: calc(var(--insp-pin-h, 44px) - 6px)`, and `--insp-pin-h` is the identity row's measured height, measured and written by `frontend/src/components/inspector/pinnedStack.js` (`applyPinHeight` / `watchPin`) from a **`useLayoutEffect`** — before paint, or the chip row is laid out with the fallback for one frame and lands inside the identity row, which is the overlap the whole change removes. A `ResizeObserver` on the pin covers what a render cannot predict (a font finishing loading, a rotation re-wrapping the label); a target without one still gets the immediate measurement. The `-6px` is the panel's own top padding, which the pin cancels with its own negative `top`. The measured value was 53 px for the `#hero` fixture at both 360 and 393 px wide.
	- The reveal runs from an effect keyed on `[touchGroup]` (panel state), not from the tap handler: it has to run *after* the new group's cards are in the DOM so the offset is measured against the height the tap produced.
	- `StyleControls` fires `onGroupChange` **only on a real change** (`if (g.id === group) return;`), so re-tapping the selected chip while reading the bottom of its own list does not yank the panel to the top. `touchGroup` starts `''` and the effect early-returns on it, so a panel that has never had a chip tapped never scrolls.
- **Element-tree hops.** `selectAncestorNode` / `selectChildNode` return a full node model, so a hop re-reads the element, its tree and its rules; the panel grows and any offset is stale by construction. A hop from a node read at the bottom left the new element's identity, preview and chip row ~2 193 px above the viewport. `panelRef` + `revealedRef` record the last revealed `objectId` and set `scrollTop = 0` for a *new* one only: re-reading the same element (a write, a Refresh, the live preview loop) must leave the user where they were reading, and clearing the selection resets the mark.
- **The error line moved into the pin.** The tree steps report failures through `setError`, and a *failed* hop is exactly the case where the user is scrolled deep in the panel. Rendering the error below the pinned block put it off screen, so a failed "go to parent" looked like a tap that did nothing. It now renders inside `.inspector__styles-pin`, and the block keeps its height when there is no error.
- **`spellcheck` is a boolean prop, not a string.** `spellcheck: 'false'` made these fields spellcheck the CSS: the DOM reflects a non-empty string as `spellcheck="true"` (verified in the page: `el.spellcheck = 'false'` → attribute `"true"`; `el.spellcheck = false` → `"false"`). Four fields in `StylesPanel.jsx` and one in `IntentPanel.jsx` were fixed. Preact sets unknown-ish lower-case attributes verbatim, so the value type is what the DOM receives.
### Styles panel: the gesture has to chain back to the page scroller
`.inspector__panel-body .inspector__styles` used to carry `overscroll-behavior: contain`, to stop the page jumping when a long property list ran out. It is the wrong trade, because `.inspector__styles` is a scroller *inside* `.app__main` and `contain` does not "stop at the end" — it swallows the gesture, so while the finger starts on the panel the page underneath cannot be scrolled **at all**, backwards or forwards.
- **Measured** in Chrome at 375 × 667 against the styles fixture, with the page scrolled down (`← Back` at `top -551`, i.e. 551 px above the viewport) and the finger parked inside the panel's visible band:
	- `contain` — three drag-down gestures over the panel left `.app__main` at `scrollTop 614 / 1489`, unchanged; the Back link never became reachable.
	- `auto` — the same three gestures moved it `614 → 439 → 264`, and dragging *up* over a panel already at its own end moved it to `175`. The panel kept its own offset (`0 / 751`) throughout: chaining only starts once the panel has nowhere left to go, which is standard nested-scroller behaviour.
- **Why the panel is where the finger is.** It is `52dvh` / 320 px floor inside a 564 px page view, so it covers ~308 px (55%) of the visible page area at 360 × 667, plus the 207 px sticky block inside it. Most of the screen is the panel, so "the gesture is contained" means "most of the screen does not scroll the page".
- **The stated cost of chaining is overstated.** The panel's own `overscroll-behavior-y` is now `auto`, and `.app__main` keeps `overscroll-behavior-y: contain`, so the chain stops at the page's own end instead of bouncing. The jump is also smaller than the old comment claimed: it is the remaining tail of the list, not a whole panel.
- **Guard the axis and the value.** `scripts/test-inspector-feature-inventory.js` had `check('styles panel contains its overscroll', /overscroll-behavior:\s*contain/.test(css))` — a regex over the whole inlined cascade, so it matched the *comment* explaining the removal and kept passing once the declaration was gone. It is now scoped to the rule's own declaration block (comments stripped) by a local `ruleBody(css, selector)` helper, and asserts the chaining value. Verified by reintroducing `contain`: the check fails.
### Styles panel: the priority (`!important`) an edit lands with
The Styles panel writes to `element.style`, and an inline declaration does **not** automatically win: a stylesheet rule marked `!important` beats a normal inline declaration. That combination used to fail invisibly.
- **Measured** in-page on a `div` with `.x { color: rgb(1, 2, 3) !important }`:
	- `setProperty('color', 'rgb(255,0,0)')` → `style.getPropertyValue('color')` is `rgb(255, 0, 0)`, so `events.js`' `applied` check is **true**, but `getComputedStyle(el).color` is still `rgb(1, 2, 3)`.
	- `setProperty('color', 'rgb(0,128,0)', 'important')` → `getComputedStyle` is `rgb(0, 128, 0)`.
- **The read-back cannot detect this**, and that is the design constraint. `getPropertyValue` reads the *inline style object*, not the cascade; it answers "is this stored on the element?", which is a different question from "is this what the page shows?". So a stylesheet-`!important` override was reported as a success, the row was written, the receipt recorded an undo entry, and the page never changed. The panel therefore has to *let the user set priority* rather than try to detect the loss — which is also the only useful behaviour, since `!important` is the fix.
- **`setInlineStyleProperty(objectId, prop, value, priority)`** takes the priority as a third in-page argument (`''` or `'important'`) and returns `{ priority }` read back off the element via `getPropertyPriority`, not echoed from the argument: the engine decides, and `setProperty(p, v, 'important')` on a property that already carries it is still `important`. The return type changed from a bare `true` at this point — every caller is in `StylesPanel.jsx` / `Inspector.jsx` and reads `.priority`.
- **Priority is part of the declaration's identity in the receipt**, so `scope.js` tracks `fromPriority` / `toPriority` alongside `from` / `to`. Two consequences worth keeping: marking an existing value `!important` is a **real change** and must not be swallowed as a same-value no-op (it can start winning a fight it was losing), and `undoPlan` carries `priority` so an undo that restores a value restores the cascade weight with it — otherwise the undo leaves the element in a state the session never created.
- **The priority travels through every read**, so it cannot be lost between an edit and the next render: `readElementStyles` returns a `priorities` map beside `inline`, `buildNodeModel` puts the priority on each `inlineProps` row, and the panel's `upsertLocal` / `applyInlineSnapshot` carry it. Without the last two, a property the user made `!important` came back looking normal the moment anything re-read the page.
### The Add-property browser (`AddPropertyBrowser.jsx` + `inspector-touch.css`)
The cards are a section of the Styles card, and the two layout notes below are what is left of the sheet that came before them (see §"The Add-property browser is a section of the panel, not a sheet" for why it moved). Both are guarded by `scripts/test-inspector-touch-controls.js`.
- **A category switch or a search must bring the controls back into view.** Selecting a category (or typing a search) replaces every card below the controls while the panel's scroller keeps its offset, clamped to the new list's maximum. Measured in the sheet this replaced: **All** read to its end (`scrollTop 2208/2208`), tap **Type** → body `183/183`, chip row at `top 63` while the body's own top was `156`, so the row sat 93 px *above* the visible region and the six new cards were all below the fold — the surface read as empty and the chips it had just offered were unreachable without scrolling up. The sheet fixed that by resetting its own scroller to `scrollTop 0`; inline there is no such scroller, so the browser calls the panel's `revealInPanel` (which measures the sticky pin first) from an effect keyed on `[group, query]` and from its open effect. Same class of problem as the group chip row, and now the same helper: the fix is not "scroll to 0", it is "put the head where the user can see it".
- **The old ceiling rules are gone, not restyled.** The sheet was `.inspector__sheet--addprop` at `86vh` / `86dvh` with a `.inspector__addprop-body` scroller, and every sheet ceiling in the cascade had to state a `vh` fallback before its `dvh` value: a browser without `dvh` (iOS Safari < 15.4, older WebViews) drops the declaration, the sheet is sized by its content, and `align-items: flex-end` then pushes its top off screen. Measured with `dvh` dropped on that sheet: 757 px tall in a 667 px viewport, top `-90`, header `-90…-27`, **Close unreachable** — `document.elementFromPoint` at its centre returned `null`, and the space above *and* below the sheet both belonged to the sheet rather than the overlay, so it could not be dismissed at all. The remaining sheets (`.inspector__sheet`, `--profiles`, `--confirm`) keep the `vh` → `dvh` pair; the browser has no ceiling to get wrong, and the test asserts both facts by name (sheet selectors absent, remaining sheets' fallbacks present).
- **`.jsx` is invisible to `node -c`.** A `useRef` used but not imported builds cleanly and then throws on the first render, taking the panel with it. `scripts/test-inspector-touch-controls.js` checks each `.jsx` file's hook import list against the hooks it calls, and `AddPropertyBrowser.jsx` is covered by the same check (`StyleControls.jsx`, `StylesPanel.jsx`).
### History navigation (Back / Forward)
The nav row carries a browser-style pair — a back arrow and a forward arrow — around the URL field. Three CDP calls back it, and two details are worth knowing before touching it.

- **Chrome's argument is `entryId`, not `historyEntryId`.** `Page.navigateToHistoryEntry` takes `{ entryId }` (confirmed against `/json/protocol`). The Back button originally shipped sending `{ historyEntryId: … }` and Chrome answered `navigateToHistoryEntry failed: Invalid parameters` on **every** tap — the route, the UI, and `scripts/test-inspector-feature-inventory.js` all existed, but the test asserted the *name of the command*, not the argument it carried, so a permanently broken control passed. `scripts/test-inspector-feature-inventory.js` now pins the field name, and `src/inspector.js` publishes history entries as `{ entryId, url, title }` (entries without a finite numeric id are dropped) so the step cannot hand Chrome a malformed argument.
- **One implementation, two directions.** `stepHistory(debuggerUrl, targetId, delta)` does the read, picks `entries[index + delta]`, and returns `{ ok: true, moved: <bool> }`; `goBackInspectorTarget` / `goForwardInspectorTarget` are one-line wrappers reporting `wentBack` / `wentForward`. A step with nowhere to go returns *before* any `navigateToHistoryEntry` command, so "no page to go forward to" costs one read and no navigation.
- **The arrows are disabled from a history read, not by guessing.** `refreshNavHistory()` (Inspector.jsx) POSTs `/api/inspector/history` and stores `{ index, canGoBack, canGoForward, entries }` in `navHistory`. `!navHistory.canGoBack` / `!navHistory.canGoForward` set `disabled` on the two arrows. A `null` snapshot (not read yet, or the read failed) leaves both tappable on purpose: the server's own verdict then answers the tap, so the row degrades to "tell me why" instead of to a dead control. Both arrows are dimmed in place (`opacity: 0.4`) rather than hidden, so the URL field never changes width when availability changes.
- **When the read runs.** On attach (right after the connection is set up), and again from `onTargetNavigated` — the `Page.frameNavigated` / `Page.navigatedWithinDocument` path — once the address bar has been updated to the URL the browser actually settled on. That is the only moment availability can change, and keying it on the settled URL is what stops a redirect chain or a history-rewrite loop from issuing one CDP read per event. A step also refreshes directly when it reports `moved: true`, because a same-document step (a hash change) does not fire `frameNavigated`; the in-flight guard makes the duplicate read a no-op. Reads are serialized by `navHistoryBusy` and a reply is dropped by `movedOffUrl(expectedUrl)` when the tab has already navigated on — a stale answer would enable the wrong arrow. `disconnect()` clears the snapshot, so a newly attached tab cannot inherit the previous tab's availability.
- **Tests.** `scripts/test-inspector-feature-inventory.js` freezes both arrows, the handler wiring, the `disabled` derivation, the 44 px floor and the dimmed-not-hidden rule for `:disabled`, plus the argument name and id filter above. `scripts/test-inspector-profiles.js` covers the HTTP surface: 400 for a missing `targetId` on all three routes (without attempting an upstream call), and a typed failure (`ETARGET_NOT_FOUND` / `ECHROME_UNREACHABLE`, never an unhandled rejection) for an unknown target. The upstream success path needs a live debug Chrome, so it is exercised by hand against a throwaway tab (open → navigate → read → back → read → forward → read → close) rather than in `npm test`.

The mobile detail sheet applies top and bottom safe-area padding at the fixed overlay level, keeping its content clear of the device status bar and home indicator. The sheet itself is `overflow: hidden` with `max-height: 80 dvh`; everything below the non-scrolling header (kv list, request/response header blocks, response body `<pre>`) lives inside an `.inspector__sheet-body` flex child that is the actual scroller (`flex: 1 1 auto; min-height: 0; overflow-y: auto; overscroll-behavior: contain`). Without that inner wrapper the kv list grew past the 80 dvh cap and a vertical swipe scrolled the page underneath instead of the sheet. The flex basis is `auto`, not `0`, so the sheet still hugs short content: when head + body intrinsic height is less than `80 dvh` the sheet sizes to its content and the body keeps its intrinsic height. Only when the parent `max-height` constraint kicks in does the body shrink and `overflow-y: auto` start scrolling, so long content scrolls within the sheet instead of overflowing it.

- **WS library** — runtime dependency `ws@^8`. Used both server-side (the `noServer` `WebSocketServer` for the upgrade handshake) and in the test mock. The mobile UI uses the browser's native `WebSocket` to talk to the server.
- **Proxy error surfacing** — a rejected upgrade (e.g. `ETARGET_NOT_FOUND`) is written as a short HTTP response with a JSON body before the socket closes. The browser's WebSocket `error` event carries no message, so `cdp.js` captures the server's close reason and the UI shows it on the status line instead of a generic "WebSocket error".
- **No new CSS framework.** The Inspector styles live in [frontend/src/inspector.css](../../frontend/src/inspector.css) (imported last by [frontend/src/style.css](../../frontend/src/style.css) so it wins on equal-specificity ties). That file is now only the entry point: it `@import`s twelve per-panel parts (`inspector-chrome.css`, `inspector-targets.css`, `inspector-pick-mode.css`, `inspector-panels.css`, `inspector-sheets.css`, `inspector-target-bar.css`, `inspector-value-suggestions.css`, `inspector-value-rail.css`, `inspector-value-kinds.css`, `inspector-intent.css`, `inspector-value-type.css`, `inspector-styles.css`) in the order the single 4 172-line file had them. Vite inlines the imports, so the built bundle and the cascade are byte-identical — the split was verified by rebuilding and diffing `frontend/dist` against the pre-split build. They re-use the same tokens (surfaces, accent, semantic colors, 4 px spacing) and follow the mobile-first rules from [.github/copilot-instructions.md](../../.github/copilot-instructions.md) §2. The panel-related selectors (`inspector__panelbar`, `inspector__panelchip`, `inspector__panel`, `inspector__panel-head`, `inspector__panel-eye`, `inspector__panels`, `inspector__panels-empty`) and the inspect chrome (`inspector__viewhead`, `inspector__sub`, `inspector__nav`, `inspector__actions`, `inspector__nav-reload`, `inspector__nav-go`) live alongside the previous `inspector__subtabs` / `inspector__subtab` rules that they replaced. The previous design's standalone `inspector__head` row (50 px) and `inspector__nav` row (50 px) totalled 100 px of chrome on a phone just to repeat what the view-head already shows; the new layout collapses the type chip + URL into a 24 px subtitle and uses an icon-only Reload glyph (32 px) + URL field + Go button on the nav row, with the Reload / Open in new tab / Show all panels / Close tab actions in a `...` overflow menu on the right of the title row. The panelbar chips carry both an inline SVG glyph and the panel label under it, so the panel name is visible on-screen at a glance instead of hiding behind an `aria-label`. Console and Network chips also surface a corner entry-count badge that lights up while the panel has live entries; Preview and Info are not countable so they stay unbadged but still render the label under their glyph for visual parity. The previous chrome above the first panel measured 197 px on a 360 px viewport; the polished panelbar still fits a single row, now at 52 px instead of 36 px to fit the label. The total chrome above the first panel went from 282 px → 197 px → ~213 px (panelbar grew 16 px to fit the label) on a 360 px viewport.

### Mobile-UI polish (this commit)

The redesign above left two rough edges that show up on a 360 px phone. This commit closes them:

- **Status line as a colored pill.** The previous design was a bare muted `<span>`. The Inspector now owns one coloured leading-dot pill (`inspector__statuspill`), and `setStatus("saved.")` is the single imperative call shape. The pill tone is derived by `classifyStatus(text)` (`idle` / `info` / `danger` / `warn` / `ok` / `busy`), so a "saved." turns green, "HTTP 502" turns red, "navigating…" pulses on the accent. Preact state replaces the previous DOM ref, so the pill re-renders on every change.
- **Panelbar chips with text labels and count badges.** Each chip is a 2-line button: SVG glyph on top, panel label underneath. Console and Network-light up a corner pill (`inspector__panelchip-badge`) showing the live entry count (capped at "999+"). The counts flow through `consoleCountRef` / `networkCountRef` refs on the event-handler state object — `pushConsole` / `pushNetwork` fire a single number per event into the parent, which updates one pair of `useState` setters (no per-event Preact render on the panel-tree path).
- **Console row 2-line wrap.** Console row height bumped from 52 → 64 px; the row body uses `-webkit-line-clamp: 2` so a long log message is readable without tap-opening the detail sheet. The time stamp moved into the meta line so the level chip + body have the row width to wrap into.
- **No CSS hooks added in vain.** The orphan fragment left over from a previous edit (`.inspector__panels-empty-hint { color... } { color... }`) is removed.

The polish is button-free for the user: existing menus, targets list, panels, and detail sheet behaviour are unchanged. The detail sheet is still the only path to stack traces, network headers, and response bodies — the polish surfaces what the user can already see without changing what they see.
- **Full-screen preview header polish.** The full-screen preview overlay (portal to `document.body`, opened from the panel header's full-screen button) used to render a single uppercase "PREVIEW" label plus a close button. That sparse header read as an unfinished surface next to the polished web-preview modal (`.wp__head` — title, host, Refresh, Size, Close) it pairs with. The overlay now renders the same `.wp__head` layout: `inspector__preview-fs-title` (one-line, ellipsis) over `inspector__preview-fs-host` (small `host[:port]` subtitle, blank for non-http(s) targets) on the left, and `inspector__preview-fs-actions` on the right with a Refresh button (calls the existing `props.refreshRef` handle, with a 350 ms `refreshBusy` cooldown so a double-tap can't double-fire capture), a Capture-size `<select>` bound to the same `VIEWPORT_PRESETS` / `viewportId` / `applyViewport` the panel's dropdown uses, and the existing close button. On narrow phones (`max-width: 430px`) the header wraps: the title block grows to `flex: 0 0 calc(100% - 52px)` so the close button can float to the top-right corner, the Refresh button hides its "Refresh" label (`inspector__preview-fs-refresh span { display: none }`) and pads to a square icon-only tap target — and because it is then a bare glyph, `.inspector__preview-fs-refresh` declares its own `justify-content: center` rather than relying on the `.btn` class it happens to carry (that class centres it today, but the mirrored `.wp__action` in the web preview viewer is not a `.btn` and had no centring, leaving its glyph at 5 px / 25 px insets; see `docs/agent/features/webpreview.md`) — and the size `<select>` widens to `flex: 1 1 0` to fill the band. The 44 px tap minimum is preserved everywhere; only the close button is absolutely positioned above the wrap row — at `top: 8px` inside the head, never `calc(var(--safe-top) + 8px)`. The overlay itself already carries `padding: var(--safe-top) 0 var(--safe-bottom)`, so the head is the close button's containing block and already starts below the status bar; adding the inset again offset the ✕ a second time (47 px on a notched phone) into the second row, where its transparent 44 px square sat on top of the size `<select>` and swallowed taps meant for the right end of the select. **This header still wraps on purpose — do not "fix" it into one row to match the Web preview viewer.** The viewer collapsed to a single 55 px row (see `docs/agent/features/webpreview.md`), but this header carries one extra control (the zoom toggle), so four 44 px controls plus three 8 px gaps leave only ~28 px for the title at 320 px (~3 characters). Measured both ways; the wrap is the better trade here. The two headers share their control *styling* but not their row model, so a change to one does not imply the other.

  `liveUrl` is sourced from the existing `Page.frameNavigated` and `Page.navigatedWithinDocument` subscriptions (the `frame.parentId` guard skips iframe navigations). `liveTitle` is fetched on demand via `Runtime.evaluate('document.title || "")` — CDP doesn't ship `document.title` as part of the navigation payload, and only fires on cross-document navigations (hash-only changes re-fire `Page.navigatedWithinDocument` but keep the same title, so we don't fetch). The Inspector wires `evaluate` through PreviewPanel as an arrow over `conn.current.cdpSend('Runtime.evaluate', { expression, returnByValue: true, awaitPromise: false })`; PreviewPanel wraps it in a ref (`evaluateRef.current = props.evaluate || null`) so the capture-loop `useEffect` doesn't take it as a dependency and rebuild the subscription on every Inspector render.

  The full implementation lives in [frontend/src/components/inspector/PreviewPanel.jsx](../../frontend/src/components/inspector/PreviewPanel.jsx) (capture-loop effect, `hostFromUrl` helper at module scope, redesigned JSX in the `createPortal` branch) and the matching styles in [frontend/src/inspector.css](../../frontend/src/inspector.css) under the `.inspector__preview-fs*` selectors. The user-facing note in [docs/features/inspector.md](../../features/inspector.md) §"Full-screen preview" describes what the user sees.
- **Responsive sizing.** A `@media (min-width: 900px)` block in [frontend/src/inspector.css](../../frontend/src/inspector.css) re-enables the "first panel grows" behaviour for tablet and desktop: the grow child becomes `flex: 1 1 auto` with the scroller / preview-frame inside it set to `flex: 1 1 auto; height: auto; min-height: 0`, and the metrics grid switches from 2 to 4 columns. Below 900 px each panel has its own intrinsic height (Preview `40 dvh`, list scrollers `32 dvh`) and the page scrolls. The breakpoint is intentionally high: at 600-899 px the four panels' intrinsic heights already exceed the available space, and the grow would just compress the non-grow panels to a sliver instead of letting the user scroll predictably between them.
- **Tab bar layout** — the bottom tab bar is a 3-column grid (`Projects / Inspector / Settings`). Inspector is a peer of the existing tabs, not a child of Settings; provider authentication lives within Settings.
- **Virtualization** — both list panels use [frontend/src/virtual-list.js](../../frontend/src/virtual-list.js). Each row is a fixed-height absolutely-positioned node, the pool is reused, and the spacer height drives the native scrollbar. The Inspector passes an optional `key` function so rows keep DOM-node identity across updates: when a network entry flips from pending to 200, or a response body loads, the same `<div>` is re-rendered in place instead of being recycled.
- **Mutable row updates** — network and console entries carry a `rev` counter that is bumped on every mutation. The virtual-list render functions diff a signature (`id|rev|status|size|duration`) against the node's previous signature and skip DOM writes entirely when nothing changed, so a busy page doesn't force-reflow the list on every CDP event.
- **State and refs.** The phase, saved debugger URL, current target, visibility set of optional panels (`visiblePanels`, hydrated from `localStorage` under `mouaif:inspector:panels` and filtered against the canonical `PANELS` allowlist), and detail item live in Preact `useState` so the Inspector re-renders when the user moves between phases or toggles a panel. The high-frequency CDP buffers (websocket, command id, pending responses, event listeners, console / network entry arrays, request map, virtual-list handles) live in `useRef` so a CDP message burst updates a ref and pushes rows into the virtual list directly. A `useEffect` on `visiblePanels` eagerly clears `consoleVL.current` / `networkVL.current` when the matching panel becomes hidden, so events.js's `if (vl)` short-circuit fires for the next CDP event instead of pushing into a destroyed virtual list. Preact is only re-rendered on phase / panel / status changes.
- **Reconnect safety.** Disconnecting rejects pending CDP commands and clears
	listeners plus the request map. Close/error events from an older socket are
	identity-checked so they cannot wipe the state of a replacement connection.
- **Backwards compatibility.** The optional-panels redesign does not change the existing REST or SSE surface; the Inspector chunk grew by ~14 KB JS and the Inspector CSS by ~3.5 KB to ship the new view. Returning users land on the same targets phase they had before; the panel visibility state defaults to all-on for a first visit and is otherwise hydrated from the `mouaif:inspector:panels` localStorage key.
- **Auto-discovery on mount.** When a debugger URL is already saved, `loadConfig` calls `loadTargets` via `setTimeout(0)` so the targets phase's status `<div>` is mounted before the request fires. Without the `setTimeout`, the call would write its status message to the setup phase's `<span>` (the only mounted status element at the time `loadConfig` resolves), and the targets phase would mount with a stale "fetching targets…" message. Returning users no longer have to retap **Discover** on every visit.
- **Strict-mode `.current` cleanup.** A previous refactor from `useRef` to `useState` left a few `debuggerUrl.current = …` and `defaultUrl.current = …` lines in `loadConfig` / `connect`. In strict mode, setting a property on a string primitive throws (`Cannot create property 'current' on string ''`), and the resulting unhandled rejection aborted the auto-discovery chain. The fix is to drop the leftover `.current` assignments and read the state value directly.
- **Server log line.** The `mouaif serve` startup banner now mentions `Web: / — mobile UI` and `CDP: /api/inspector/ + WS /api/inspector/proxy` so users can see at a glance.

- **Close-tab in-app confirmation.** Delete-a-tab is destructive, so the Inspector never sends `POST /api/inspector/close` until the user confirms. The previous design used `window.confirm`, which some embedded web views (PWA-style webviews on iOS, in-app browsers, the inspector surface viewed inside a child frame) auto-dismiss and return `false` without rendering a dialog. When that happens the close handler short-circuits at the early-return and the user sees the button as inert: no status pill update, no network round-trip, and the targets list still shows the tab. Replaced with [frontend/src/components/inspector/ConfirmSheet.jsx](../../frontend/src/components/inspector/ConfirmSheet.jsx), a small alertdialog overlay rendered by [frontend/src/components/Inspector.jsx](../../frontend/src/components/Inspector.jsx) that captures the pending close as `closePending` state (— `{ action: 'row' | 'attached', target }`). Two entry points share one sheet: the targets-list `…` menu (each row) and the inspect-phase header overflow menu (InspectActionsMenu). Confirming dispatches to `runCloseRow` (no live connection, just `POST /api/inspector/close` + `loadTargets`) or `runCloseAttached` (live connection survives the round-trip and is torn down after the close succeeds so status messages still reach the pill), then refreshes the targets list. Cancel just clears the state — no status pill is restored and no network call is made. The sheet reuses the `.inspector__overlay` / `.inspector__sheet` primitive from the detail sheet (`.inspector__sheet--confirm` shrinks `max-height` from 80 dvh to 50 dvh to fit a one-line message + two 44 px buttons on the smallest phones; `.inspector__sheet-body--confirm` adds extra safe-area padding for the home indicator; `.inspector__confirm-actions` lays out Cancel + the destructive Close-tab button on a row with the `data-danger="1"` confirm button using `--danger` background). The replaceable hook is `requestClose(action, target)`, called from `actionTarget("close", t)` in the targets-list path and from `closeAttachedTarget()` in the inspect-phase path.
