PWA — install, offline shell, update prompts

Overview

The PWA scaffolding covers four things:

  • A manifest.webmanifest declaring the app's display metadata, theme color, start URL, scope, and icon set. Vite copies it verbatim from frontend/public/manifest.webmanifest into dist/, where the Node server serves it at /manifest.webmanifest with the application/manifest+json MIME.

  • A tiny, hand-rolled service worker (no Workbox, no dependencies) that precaches the app shell, runs cache-first for fingerprinted JS/CSS/icons and network-first for navigation, and bypasses /api/*, /events, /data, /oauth/*, cross-origin, and any non-GET request. Because the SW is registered with scope: '/', those live endpoints are bypassed explicitly rather than by a path-prefix shell like the old / layout.

  • iOS-specific meta tags and an apple-touch-icon so an iPhone user can tap Share → Add to Home Screen and get a standalone shortcut with the mouaif glyph as its home-screen icon.

  • Two app-state banners in the app shell: a thin offline indicator and a "new version ready" prompt. Browsers may still expose their own install affordance in the URL bar, but mouaif no longer shows an in-app install banner just because the page became installable.

  • A viewport-locked, responsive shell for installed mode. html/body are locked to the viewport (overflow: hidden; overscroll-behavior: none) so the document can never scroll or rubber-band against the inner scrollers. The document height tracks the dynamic viewport (100dvh) in the browser; installed standalone mode switches to the large viewport (100lvh) because it has no browser toolbar, and #app becomes an absolutely-positioned full-height box so it reaches the physical bottom edge instead of stopping above the home indicator (the dead margin below the composer). Individual views own any necessary scrolling, preventing double-scroll or horizontal overflow on narrow screens. The compact app header absorbs the top safe-area inset and centers its brand inside the status-bar area instead of reserving an additional row below the notch. Bottom controls use opaque fallbacks and paint through the home-indicator safe area so the inset remains protected without appearing as a detached blank margin.

Usage

There is no command to run. The PWA plumbing is built into every npm run build:web. After the build, opening http://127.0.0.1:5732/ in a browser exposes the install affordance the browser already supports:

```bash
node frontend/build/generate-icons.js
node frontend/build/check-icons.js

npm run build:web

node scripts/test-pwa.js
```

On Chrome (desktop and Android), the browser may show an "Install" icon in the URL bar once the manifest is reachable. mouaif does not show its own in-app install banner on first load. On iOS Safari, the user taps Share → Add to Home Screen.

Once installed:

  • Launching the shortcut opens http://127.0.0.1:5732/ in a standalone window (no URL bar, no navigation chrome).

  • The standing screen icon is the lowercase mouaif wordmark on the blue gradient, rendered in the same ink as the in-app logo. It is a vector-style stroke mark (round-capped strokes, anti-aliased), not the older blocky pixel font. The 32px favicon, where six letters cannot fit legibly, falls back to the single bold m used by the in-app logo.

  • A first launch with the server reachable primes the cache so a later offline launch still renders the shell.

Migration from the old /web/ install

mouaif used to be installed with a web/ prefix: the manifest declared id, scope and start_url of /web/, and the service worker was registered as /web/sw.js under a /web/ scope. After the frontend moved to the root (/), a PWA installed from that older build does not upgrade in place:

  • The new manifest uses id: "/", which the browser treats as a different app identity — it will not morph the old /web/ install into the new one.

  • The legacy route sends /web/ → 301 / . That lands outside the old app's /web/ scope, so the OS/browser drops display: standalone and opens the root in a normal browser tab — the most visible symptom: "launching the PWA opens the browser instead of the app."

  • The old /web/-scoped service worker and its caches are a separate, root-out-of-scope registration the new / SW cannot reach or clean up.

    Because of this, re-installation is required once after the move. The migration is a one-time manual step (the app can't reliably re-install itself from within a redirect that has already left the old scope):

  1. Open http://host:5732/ in the browser once (not the stale home-screen shortcut) so the new /-scoped manifest and service worker are fetched and registered.

  2. Remove the old home-screen shortcut / installed app (iOS: Share → ✕ → Remove from Home Screen; Android / Chrome: Uninstall or ✕ on the app icon).

  3. Re-add it (iOS: Share → Add to Home Screen; Chrome: Install prompt) — it now installs from / with standalone mode.

    Opening /web/ in a browser still 301-redirects to / so old bookmarks and any browser-tab reference keep working; only the installed shortcut needs the re-add.

Behavior

  • Manifest URL. /manifest.webmanifest. The Node server emits application/manifest+json; charset=utf-8 and a 5-minute Cache-Control: public, max-age=300 so the browser re-fetches the manifest on the next session without keeping a stale one around forever.

  • Service worker URL. /sw.js. Served with Service-Worker-Allowed: / (so the script installed from /sw.js can claim the entire / prefix) and Cache-Control: no-cache (so the browser always revalidates the script and the activate handler can evict the old cache on the next load). Registration uses scope: '/'.

  • Cache strategy.

    • install precaches the shell (/, the manifest, the three icons). Best-effort: a single failed icon does not block activation.

    • activate deletes any cache whose name doesn't match the current build hash, then clients.claim() so the new version is live without a navigation.

    • fetch:

      • Same-origin GET under the root whose path is a PWA asset → handled.

        • Navigation request (mode === navigate or Accept: text/html) → network-first with a fallback to the cached shell on offline.

        • Static asset → cache-first (fingerprinted filenames, so a cache hit is always valid).

      • Cross-origin, /api/*, /events, /data, /oauth/*, the favicon, non-GET, and SSE GETs → bypassed. The chat surface stays live; the SW never sits in front of a streaming response.

  • Hashed JS/CSS assets are served with Cache-Control: public, max-age=31536000, immutable. The fingerprint changes on every build, so a stale copy is GC'd by the next deploy.

  • Icons. 192 × 192 and 512 × 512 "any purpose" icons, plus a 512 × 512 "maskable" variant for Android adaptive icons. A 180 × 180 PNG doubles as the iOS apple-touch-icon, and a 32 × 32 PNG is the favicon. All but the favicon carry the full mouaif wordmark — a hand-rolled 5px-tall pixel font drawn in the same ink as the in-app logo on the brand-gradient tile (frontend/build/generate-icons.js, no image library at build time). The 32 px favicon keeps the compact single-"m" glyph, since six letters cannot rasterize legibly at that size. The maskable variant renders the wordmark at ~66% of the tile side so all ink stays inside the ~80% safe zone that Android's adaptive-icon mask clips to.

  • Update flow. A first installation activates immediately because there is no old app bundle to protect. Later SW updates remain waiting and the page shows an "A new version is ready." banner as soon as installation finishes, without requiring a manual page reload. Registration observes an update already in progress as well as future updatefound events, then performs an explicit update check to cover browsers that finish their automatic check before listeners are attached. While the app remains visible it checks the no-cache worker script once per minute, so a long-running standalone session discovers deployments without a navigation; returning to a hidden app also triggers a check. The page retains the installed worker reference because some engines do not expose it through registration.waiting immediately. Tapping Reload posts { type: 'SKIP_WAITING' } to that worker; the worker activates and the controllerchange listener reloads once, because applyUpdate() recorded the tap (see the next two bullets). Existing sessions never reload merely because an update finished installing, and never reload for a controller change they did not ask for.

  • A first install does not reload the page it claims. The worker's activate handler calls clients.claim(), which takes control of the page already on screen and fires controllerchange on a window that loaded UNCONTROLLED. The handler used to reload on every controllerchange, so the first visit to an origin installed the worker, painted the app, and then threw that page away and loaded it again — a white flash, a second document load, and a second round of chat requests on what looked like a normal first open.

  • A controller change the user did not ask for never reloads the page. clients.claim() runs on every activation, so it also fires controllerchange on windows that loaded CONTROLLED: a deploy another tab accepted, or a worker evicted and then re-registered by a later visit, claims every open client. An earlier rule keyed the decision on "was this page controlled when it loaded?", which answered yes for those tabs and reloaded them anyway — a long chat tab reloading at a moment tied to deploys and worker churn rather than to anything the user did. frontend/src/sw-controller-reload.js now reads intent instead of control state: a controller change reloads only when acceptedUpdate is set (the user tapped Reload on the banner), updateApplied confirms the accepted worker actually left the waiting slot, and a controller owns the page. A claim nobody requested is something that happened to the page, so it is left alone; the next natural navigation picks up the new bundle.

  • Accepting an update still reloads. Tapping Reload on the banner posts SKIP_WAITING, which activates the waiting worker and fires controllerchange. applyUpdate() records that intent in acceptedUpdate before the post, so the tap that asked for the update is part of the decision — including on a first session, whose page loaded uncontrolled and would otherwise never be identified as the one that asked. Intent also covers the case where an engine delivers the controllerchange before the SKIP_WAITING post resolves. Recording intent before the post matters: reading a load-time flag when the event fires sees the value clients.claim() has already flipped, which is how the two cases became indistinguishable.

  • An accept intent is one-shot, and is refused when the worker it was given for had already activated. This is the reported random reload. waitingWorker is retained deliberately (some engines do not expose registration.waiting immediately), so a tap could post SKIP_WAITING to a worker that was already active — its activation finished, or another tab accepted the same update first. That post is a no-op: no activation follows, no controllerchange arrives, the tap appears to do nothing, and the armed acceptedUpdate stayed latched. The next activation then claimed this page (clients.claim() runs on every activation), matched the stale intent, and reloaded a tab whose user had asked for nothing — minutes or hours later, at a moment tied to somebody else's deploy. Two changes close it. First, applyUpdate() refuses a worker that has left the waiting slot and dismisses the stale banner instead of arming an intent that can never match. Second, the intent is now scoped to a specific worker and the decision requires updateApplied (that worker has left the waiting slot, so this activation is the one the tap caused), and takeAcceptedUpdate() consumes the intent — so a single tap can never reload twice, and a controller change the tap did not cause clears the intent rather than spending it.

  • The waiting slot is spelled installed, not waiting. ServiceWorkerState has no waiting member: while an update is waiting, registration.waiting.state is installed and registration.active.state is activated (verified against Chrome 140). A guard written against a 'waiting' string therefore refuses every genuine update and no accepted tap would ever reload, so the "has it left the waiting slot?" question is answered by isUpdateStillPending() in frontend/src/sw-controller-reload.js — true for parsed / installing / installed, false for activating / activated / redundant. scripts/test-sw-controller-reload.mjs pins the vocabulary, the stale-intent refusals, the consuming helper, and the positive path (the tap whose own activation follows still reloads).

  • Offline indicator. The offline banner ("You are offline. Showing the last cached view.") appears when the browser fires offline or when a same-origin app-shell fetch fails. API, SSE, OAuth, data, and favicon requests do not affect this state. Multiple banners stack: offline at the top, update immediately below.

  • Scope. Strictly the app shell at /. /api/settings, /api/ai/*, /events, /data, /oauth/callback, and any future same-origin endpoint are untouched by the SW. The SW logs [mouaif-sw] warnings for visible problems (partial precache) but does not throw — the chat UI works as a normal web page if the SW is unavailable (private mode, restrictive embedding, etc.).

  • Dev mode. npm run dev:web does not register the SW. Stale code in the cache would defeat Vite's HMR, so registration is a no-op when import.meta.env.PROD is false.

  • No flash before the stylesheet. frontend/index.html carries a one-line inline rule, <style>html{background:#0a0d12}</style>, in <head>. The document used to have no background of its own — every surface came from the @import-ed index CSS — and that external stylesheet is requested before the module script runs, so between the document commit and the arrival of the CSS the page painted the browser's default canvas instead of the app. Measured on a headless Chrome at 390 × 844: a document with the color-scheme: dark meta and no stylesheet paints #121212, and with no hint at all it paints #fff, against an app whose --bg is #0a0d12 / rgb(10, 13, 18). That gap is one or more frames of a lighter, near-grey full-screen fill between a reload and the first render — reported as "grey flashes with page reload". The inline rule is in the document, so it applies at the first paint, and it reuses the literal value of --bg from frontend/src/base.css, so the swap to the bundle's own html background is an invisible repaint of the same base colour rather than a step. The two rules set the same background property at the same specificity, so their order is what matters as well: the inline block sits before the <link rel="stylesheet"> Vite appends to the end of <head>, which is what lets the bundle's rule take over and add the accent glow. scripts/test-index-first-paint.mjs pins all three facts — the inline rule exists in <head>, its colour equals the --bg token, and in the built dist/index.html it still precedes the bundle's stylesheet — so a drift in any of them fails the test.

    • The registered service worker hides this on a warm profile (it precaches index.html and serves the CSS cache-first), which is why the symptom reads as intermittent. It is reproducible on a first visit, a hard reload with cache disabled, a fresh/private profile, and any engine that renders the document before the stylesheet lands.
