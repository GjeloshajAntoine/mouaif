Tool groups

Overview

Tool groups decide which tool belongs to which group in every tool list the app renders. One list, frontend/src/toolGroups.js, drives the chat Tools card, the composer tools popup, project settings, the Custom prompts preset tree, and the agent editor. Moving a tool between groups is a one-line edit in that file — no surface keeps its own copy of the mapping.

Usage

Nothing to configure: the grouping is a property of the app, not a per-project setting. What you see is what toolGroups.js declares.

Tools the table cannot show

Two advertised tools are conditional, so they have no row — they are switched on by something other than a group:

  • activate_skill — added only when the project has a non-empty Agent Skills catalog, and its name enum is the enabled skills. It has no group row and no authorization gate of its own: it is governed by the Skills switches in Settings → Project, and a call is answered without an approval card because it is a read-only lookup constrained to that enum.

  • mcp__<server>__<tool> — one per tool of every configured MCP server. Their rows live outside this model, in the MCP registry.

Why webpreview sits in Chats

webpreview used to be a group of its own. It is a leaf of the Chats family now, because the row that is a chat should list everything the model can do with one — and showing the user a page is one of those things. A stored tools.webpreview keeps working as that leaf's override.

Families

Every group with an Off / Ask / Allow control is a family: one gate key under tools.<key> in the project (or app, or chat) settings. A single-tool family's key is the tool name. A multi-tool family (Subagent → subagent, File tools → file, Chats → chats, mouaif → mouaif) has one key for all of its leaves, and each leaf may also carry its own entry:

{
  "tools": {
    "chats": { "mode": "allow" },
    "delete_chat": { "mode": "off" }
  }
}

The same precedence applies to every multi-tool family: a leaf off always wins, a family allow beats any other leaf value, otherwise the leaf entry wins over the family. A family off hides every leaf from the model.

A single-tool group (shell) is its own gate, so its key is just the tool name. Every tools.<name> these pages name is one of the keys the server resolves: a family gate, a single-tool gate, or a family leaf that may carry its own override. A key the server does not know is stored and never read, so it silently does nothing — scripts/test-tool-groups.mjs fails on one.

Two things are deliberately outside this model: activate_skill (no row and no tools.* key — it is governed by the Skills switches in Settings → Project) and the mcp__<server>__<tool> specs (they resolve through .mcp.json). Neither may be named as a tools.<name> key on these pages.

Working with the tree

Group rows carry a checkbox that flips every child at once (showing a half-check when only some children are on) and, in project settings and the chat, an Off / Ask / Allow segment that edits the family gate. In project settings each leaf of a multi-tool family also has its own segment for a per-leaf override. See Tool tree for the full row anatomy.

What a family allow covers

Because restart_app, list_features and group_cli are mouaif leaves, a family allow — including one earned by choosing Always allow on any mouaif call — also lets the assistant restart the app and run a batch of shell commands without asking. Turn either off on its own with a tools.restart_app / tools.group_cli leaf override if you want the family open and that tool gated. list_features is read-only metadata: it is never shown an approval card, but an off on the family or on the leaf hides it from the model. group_cli is the opposite — it runs commands, so it uses the ordinary approval card.

The Chats family behaves the same way, with one deliberate exception: ask_user is a binary tool. A tools.chats allow covers every chat function including task, report_progress and webpreview, but it can never auto-answer a question — an ask_user call always reaches the user, whatever the family or the leaf says. Only off (tools.chats.mode, or a tools.ask_user leaf override) hides it. report_progress is read-only UI metadata: it is answered without an approval card too, but an off on the family or the leaf still hides it from the model. webpreview keeps its own approval card — a family allow (or an Always allow earned on any Chats call) lets the assistant capture a page without asking.
